## 배경과 목적

원격 DB에서 `FINAL_JUDGMENT_STATUS` 코드 그룹이 누락되어 결과 입력의 합격·불합격 선택지가 표시되지 않는 문제를 복구한다.

## 범위

### 포함

- `FINAL_JUDGMENT_STATUS` 코드 그룹을 멱등하게 생성·활성화한다.
- `PASS / 합격`, `FAIL / 불합격` 상세 코드를 멱등하게 생성·활성화한다.
- 원격 migration 적용과 데이터 재검증을 수행한다.

### 제외

- 결과 입력 UI 구조 변경
- 기존 검사성적서 및 측정이력 데이터 변경
- 다른 공통코드 그룹 변경

- [x] 원격 DB에 최종판정 코드 그룹이 존재하고 활성 상태다.
- [x] 합격·불합격 상세 코드가 존재하고 활성 상태다.
- [x] 후속 migration dry run에서 원격과 로컬이 일치한다.

## 현재 구현 조사

- 관련 route/component: `inspection-measurements/inspection-measurement-sheet.tsx`, `inspection-reports/data.ts`
- 관련 Supabase table/bucket: `code_groups`, `code_details`
- 재사용할 기존 패턴: 공통코드의 `group_code`, 그룹 내 `code` unique constraint와 upsert
- 문서와 구현의 차이: 기존 migration은 상세 코드만 보장하고 선행 코드 그룹의 존재를 전제로 했지만 원격 DB에는 해당 그룹이 없다.

## 설계

### UI와 반응형

- 모바일/태블릿/데스크톱: UI 변경 없음. 복구된 공통코드가 기존 최종판정 영역에 표시된다.
- 로딩/빈 상태/오류/권한: 기존 동작 유지
- 접근성: 기존 radio label 구조 유지

### Server/Client 경계

- Server Component/Action: 기존 공통코드 조회와 저장 검증을 유지한다.
- Client Component/Zustand: 변경 없음

### 데이터와 Supabase

- schema 변경: 스키마 변경 없이 누락된 공통코드 기준 데이터를 복구한다.
- PK/FK/index: 기존 제약과 인덱스 유지
- RLS 정책: 변경 없음
- Storage bucket/path/policy: 해당 없음
- migration과 rollback: 새 보정 migration으로 upsert한다. rollback 시 새 상세 코드와 그룹을 삭제할 수 있으나 참조 데이터가 생기면 삭제하지 않고 비활성화해야 한다.

## 변경 계획

1. 코드 그룹과 상세 코드를 함께 보장하는 보정 migration을 작성한다.
2. 원격 dry run 후 migration을 적용한다.
3. 원격 데이터와 migration 상태를 재검증한다.

## 위험과 승인 사항

- 적용 후 저장된 검사성적서가 상세 코드를 참조할 수 있어 단순 삭제 rollback보다 비활성화 rollback이 안전하다.
