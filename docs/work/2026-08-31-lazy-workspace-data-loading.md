## 배경과 목적

현재 `(app)` 레이아웃은 로그인 후 작업영역을 만들 때 성적서, 측정결과, 측정이력, 품목, 오차범위와 코드 데이터를 한꺼번에 조회한다. 사용자가 열지 않은 화면의 데이터까지 가져오므로 최초 로딩 비용이 커지고, 품목·오차범위 화면의 조회 버튼은 DB가 아니라 메모리 데이터만 필터링한다. 각 화면을 처음 열 때 필요한 데이터만 조회하고, 조회 버튼이 있는 화면은 버튼을 누를 때마다 조건에 맞게 DB를 다시 조회하도록 변경한다.

## 범위

### 포함

- 앱 레이아웃의 전체 업무 데이터 선조회 제거
- 성적서 관리, 결과 입력, 측정 이력, 품목관리, 오차범위관리와 코드관리 패널의 최초 표시 시 화면별 데이터 조회
- 이미 열린 탭은 닫기 전까지 마운트와 입력·선택·스크롤 상태 유지
- 품목관리와 오차범위관리 조회 버튼을 Supabase 서버 재조회 방식으로 전환
- 기존에 서버 검색을 사용하는 성적서 관리와 측정 이력도 조회 버튼마다 DB 재조회 유지 및 확인
- 로딩, 재조회 중 상태, 오류와 빈 결과 처리
- 직접 URL과 작업영역 탭에서 동일한 조회 결과 유지

### 제외

- DB 테이블, 컬럼, RLS와 migration 변경
- 검색 조건, 컬럼 구성과 업무 기능 변경
- 자동 새로고침, 실시간 구독과 클라이언트 캐시 라이브러리 도입
- 페이지 크기나 페이지네이션 정책의 별도 변경

## 완료 조건

- [x] 최초 앱 진입 시 열지 않은 업무 화면의 목록 데이터를 조회하지 않는다.
- [x] 각 탭은 실제로 처음 표시될 때 필요한 데이터를 한 번 조회한다.
- [x] 닫지 않은 탭을 전환하면 기존 화면 상태를 유지하며 불필요한 최초 조회를 반복하지 않는다.
- [x] 조회 버튼이 있는 화면은 클릭할 때마다 현재 조건으로 서버 DB를 다시 조회한다.
- [x] 초기화 후 조회도 빈 조건으로 DB를 다시 조회한다.
- [x] 직접 URL과 작업영역이 동일한 서버 조회 규칙과 오류 처리를 사용한다.

## 현재 구현 조사

- 관련 route/component: `src/app/(app)/layout.tsx`, `workspace-shell.tsx`, `workspace-panels.tsx`, 각 업무 route의 `page.tsx`, `actions.ts`, `data.ts`
- 관련 Supabase table/bucket: 기존 업무 화면에서 조회하는 테이블 전체. 스키마 변경 없음.
- 재사용할 기존 패턴: `searchInspectionReports`, `searchMeasurementHistory` 서버 조회 action과 기존 화면별 page query
- 문서와 구현의 차이: 탭 상태 유지 규칙은 구현되어 있지만, 패널 데이터는 `layout.tsx`에서 모든 화면에 대해 선조회된다.

## 설계

### UI와 반응형

- 모바일: 현재 화면 레이아웃을 유지하고 최초·재조회 로딩 상태를 목록 영역에 표시한다.
- 태블릿: 기존 container 반응형과 독립 스크롤을 유지한다.
- 데스크톱: 단일·분할 패널 모두 각 패널이 독립적으로 조회하고 상태를 유지한다.
- 로딩/빈 상태/오류/권한: 최초 로딩과 재조회 로딩을 구분하고, 기존 오류·빈 상태 문구를 유지한다. 관리자 화면 권한은 기존 서버 검증을 유지한다.
- 접근성: 조회 버튼의 disabled/busy 상태와 결과 영역의 알림을 제공하고 키보드 submit을 유지한다.

### Server/Client 경계

- Server Component/Action: 인증·권한 확인과 Supabase 조회는 서버 action/data 함수에서 수행한다. 검색 조건은 서버에서 길이 제한과 escape를 적용한다.
- Client Component/Zustand: 패널이 실제 표시됐을 때 최초 action을 호출하고 결과·조회조건·선택 상태를 패널 지역 상태에 보관한다. 업무 데이터는 Zustand에 저장하지 않는다.

### 데이터와 Supabase

- schema 변경: 없음
- PK/FK/index: 변경 없음. 기존 검색 조건과 정렬을 유지한다.
- RLS 정책: 변경 없음. 현재 사용자 세션과 기존 RLS를 그대로 사용한다.
- Storage bucket/path/policy: 품목 이미지 URL 조회 방식은 유지하며 해당 화면이 열릴 때만 수행한다.
- migration과 rollback: migration 없음. 문제 발생 시 레이아웃 선조회와 기존 props 전달 구조로 코드 rollback 가능하다.

## 변경 계획

1. `layout.tsx`를 권한별 허용 탭과 지연 패널 구성만 담당하도록 축소한다.
2. 작업영역에서 패널의 표시 여부를 전달해 아직 한 번도 표시되지 않은 패널은 조회하지 않도록 한다.
3. 각 업무 도메인에 인증·권한 검증이 포함된 최초 조회 함수를 정리하고 패널별 로딩 상태를 연결한다.
4. 품목관리와 오차범위관리 검색을 클라이언트 배열 필터에서 서버 조건 조회로 전환한다.
5. 기존 성적서/이력 조회가 버튼마다 서버 action을 호출하는지 유지·검증한다.
6. 등록·수정·삭제 후 현재 화면 데이터가 일관되게 갱신되는지 확인한다.
7. 직접 URL, 탭, 2분할과 탭 재전환을 검증한다.

## 위험과 승인 사항

- 최초 화면 진입 시 해당 화면의 로딩 표시가 짧게 나타날 수 있다.
- 탭을 닫았다가 다시 열면 새 패널로 간주하여 최신 데이터를 다시 조회한다.
- 서로 다른 탭에서 같은 원본 데이터를 쓰더라도 화면별로 필요한 시점에 별도 조회한다. 전역 데이터 캐시는 두지 않는다.
- DB 구조와 정책은 변경하지 않는다.

## 결과

- 변경: 레이아웃의 업무 데이터 선조회를 제거하고 실제로 표시된 탭만 화면별 Server Action으로 조회하도록 전환했다. 품목·오차범위 조회와 초기화는 매번 현재 조건으로 DB를 재조회하며, 기준정보 변경 후에도 현재 조건으로 목록을 갱신한다.
- 검증: `npm run lint`, `npx tsc --noEmit`, `npx next build --webpack`, `git diff --check`를 통과했다. 성적서 관리와 측정 이력의 조회 버튼이 기존 서버 검색 action을 호출하는 것도 코드로 재확인했다.
- 미실행: 로컬 브라우저 세션이 로그인 화면이어서 관리자 탭의 실제 모바일·태블릿·데스크톱, 단일·2분할 상호작용 검증은 실행하지 못했다. 비로그인 상태에서 `/`가 `/login`으로 이동하는 것은 확인했다.
- 남은 위험/후속 작업: 데이터가 매우 많아질 경우 품목·코드 화면의 서버 페이지네이션은 별도 작업으로 검토한다.
