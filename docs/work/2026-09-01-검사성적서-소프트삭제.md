## 배경과 목적

검사성적서를 물리 삭제하면 과거 측정이력까지 cascade로 삭제된다. 마스터에 삭제 여부를 기록해 활성 업무 화면에서는 숨기되 과거 측정이력은 보존한다.

## 범위

### 포함

- `inspection_reports.is_deleted` 컬럼과 활성 조회 partial index 추가
- 삭제 Action을 `is_deleted = true` 업데이트로 변경
- 성적서 관리, 결과 입력 선택과 홈 최근 성적서에서 삭제 행 제외
- 삭제된 성적서의 신규 측정 저장 차단
- 측정 이력 스냅샷 유지 및 이력 메뉴 조회 유지

### 제외

- 삭제 성적서 복구 UI
- 관리자 휴지통 화면
- 등록 실패 rollback용 내부 물리 삭제 변경

## 완료 조건

- [x] 삭제 시 마스터 행의 `is_deleted`가 true가 된다.
- [x] 삭제된 성적서는 활성 관리·결과 입력·홈 화면에 나타나지 않는다.
- [x] 삭제 전 측정 이력은 측정 이력 메뉴에서 조회할 수 있다.
- [x] 이미 열린 삭제 성적서에 측정결과를 추가 저장할 수 없다.
- [x] 신규 성적서는 기본적으로 `is_deleted = false`다.

## 현재 구현 조사

- 관련 route/component: 성적서 관리 Action, 결과 입력 검색, 홈 데이터
- 관련 Supabase table: `inspection_reports`, 측정 이력 테이블
- 관련 RPC: `save_inspection_measurement_entry`
- 문서와 구현의 차이: 현재 삭제 Action이 실제 DELETE를 실행해 cascade 이력 삭제 위험이 있다.

## 설계

### UI와 반응형

- 기존 삭제 확인 Dialog를 유지한다.
- 삭제 성공 후 현재 검색 조건으로 목록을 재조회한다.
- 반응형과 접근성 변화는 없다.

### Server/Client 경계

- Server Action은 인증 사용자만 실행 가능한 전용 RPC로 소프트 삭제를 수행하고 삭제 대상이 없으면 오류로 처리한다.
- Client는 기존 성공/오류 상태와 목록 갱신 흐름을 재사용한다.

### 데이터와 Supabase

- schema: `is_deleted boolean not null default false`
- index: 활성 성적서 최신순 조회 partial index
- RLS: 기존 일반 update owner/admin 정책은 유지하고, 로그인 사용자는 권한이 제한된 전용 RPC로 `is_deleted`만 변경
- DB 보호: 삭제된 성적서의 후속 update를 trigger로 차단해 RPC와 직접 수정 경로에 동일하게 적용
- migration: 추가 migration으로 적용한다.
- rollback: 활성화된 삭제 행을 false로 복구한 뒤 컬럼·인덱스를 제거할 수 있으나 소프트 삭제 의미가 사라진다.
