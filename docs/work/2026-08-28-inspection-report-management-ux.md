## 배경과 목적

성적서가 많아져도 원하는 성적서를 빠르게 찾고, 선택한 성적서의 핵심 정보와 검사항목을 긴 스크롤 없이 확인·수정할 수 있도록 성적서 관리 화면의 정보 밀도와 탐색 흐름을 개선한다.

## 범위

### 포함

- 상단 도구 영역에 단일 검색 유형 선택, 검색어, 정렬, 전체 건수, 성적서 등록 배치
- 검색 유형: 통합검색, 기종, 품번/도번, 품명, 고객명, 업체명
- 왼쪽 성적서 목록을 행 높이 약 68px의 조밀한 목록으로 변경
- 목록에 페이지당 50건, 이전/다음 페이지와 검색 결과 건수 표시
- 선택 행에는 품번/도번, 기종·품명, 고객명과 검사항목 수를 명확히 표시
- 오른쪽 상세 상단에 선택 성적서 식별정보와 수정·삭제 행동 고정
- 상세 내용을 `기본정보`와 `도면·검사항목` 탭으로 분리해 세로 스크롤 축소
- 값이 없는 항목은 `-` 대신 빈칸 또는 `미입력` 보조 표현으로 통일
- 좁은 작업 패널에서는 목록과 상세를 세로 배치하고 container 기준 반응형 적용
- 검색·페이지·선택 상태는 해당 패널의 지역 상태로 유지

### 제외

- DB schema, RLS, index와 migration 변경
- 성적서 등록·수정 Dialog의 필드 또는 저장 규칙 변경
- 서버 측 검색·페이지네이션 API 도입
- 성적서 다중 선택·일괄 삭제·Excel 내보내기

## 현재 구현 조사

- 관련 route/component: `inspection-reports/page.tsx`, `inspection-report-management.tsx`
- 관련 Supabase table/bucket: 변경 없음
- 재사용할 기존 패턴: 측정 이력의 검색 유형 Select, workspace container query, 단일 선택 상태
- 문서와 구현의 차이: 현재 마스터 목록은 전체 행을 큰 카드형 버튼으로 렌더링하며 검색·정렬·페이지 구분이 없다.

## 설계

### UI와 반응형

- 모바일/좁은 분할 패널: 도구 영역 줄바꿈, 목록 전체 너비, 선택 상세를 목록 아래 배치
- 태블릿: 목록 340px + 상세, 공간 부족 시 상세 탭 내부 가로 스크롤 허용
- 데스크톱: 목록 380px + 상세 가변 너비, 양쪽 독립 스크롤
- 로딩/빈 상태/오류/권한: 검색 결과 없음과 전체 데이터 없음 상태를 구분
- 접근성: 검색 label, 탭 role/aria, 선택 행 aria-pressed, 페이지 버튼 접근성 이름 유지

### Server/Client 경계

- Server Component/Action: 기존 데이터 조회와 저장 Action 유지
- Client Component/Zustand: 검색·정렬·페이지·상세 탭은 지역 상태. 열린 탭 store에는 복제하지 않음

### 데이터와 Supabase

- schema 변경: 없음
- PK/FK/index: 변경 없음
- RLS 정책: 변경 없음
- Storage bucket/path/policy: 변경 없음
- migration과 rollback: 해당 없음

## 변경 계획

1. 검색·정렬·페이지 파생 상태와 목록 메타데이터를 구성한다.

3. 좁은 패널과 분할 화면 container 반응형을 조정한다.
4. 키보드 선택, 빈 상태, lint·typecheck·build를 검증한다.

## 위험과 승인 사항

- 이번 단계의 페이지네이션은 이미 조회된 데이터를 화면에서 50건씩 나누는 방식이다. 수천 건 규모에서 네트워크 조회까지 줄이려면 workspace 전체 데이터 로딩을 분리하는 후속 Architecture 작업이 필요하다.
- 등록·수정 Dialog 자체의 재설계는 화면 탐색 개선 후 별도 작업으로 다룬다.
