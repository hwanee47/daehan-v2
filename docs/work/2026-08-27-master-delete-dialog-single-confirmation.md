## 배경과 목적

기준정보에서 선택한 행을 삭제한 뒤 목록이 갱신되면 선택 대상과 삭제 다이얼로그의 `key`가 다음 행으로 바뀌지만, 부모의 열림 상태가 닫히기 전이라 다음 행의 삭제 확인창이 다시 표시된다. 삭제 요청 자체는 `seq`가 일치하는 한 건만 처리한다. 사용자가 선택한 한 건을 한 번 확인해 삭제한 뒤 삭제 흐름이 끝나도록 한다.

## 범위

### 포함

- 코드그룹 및 상세 코드 삭제 다이얼로그
- 품목 및 품목상세 삭제 다이얼로그
- 오차범위 삭제 다이얼로그
- 삭제 성공 시 다음 행을 대상으로 확인창이 재표시되지 않도록 열림 상태 처리

### 제외

- DB schema, RLS, migration 변경
- 삭제 가능 조건과 연관 데이터 정책 변경
- 다중 선택 및 일괄 삭제 기능
- 기준정보 외 업무 화면의 삭제 UX 변경

- [x] 삭제 실패 시 현재 대상과 오류 메시지를 유지해 사용자가 재시도하거나 취소할 수 있다.

## 설계

### UI와 반응형

- 모바일: 기존 Portal 삭제 다이얼로그의 크기와 배치를 유지한다.
- 태블릿: 기존 동작을 유지한다.
- 데스크톱: 기존 동작을 유지한다.
- 로딩/빈 상태/오류/권한: pending 중 중복 제출을 막고, 실패 시 기존 오류 표시를 유지한다.
- 접근성: 기존 focus, Escape, 취소 버튼 동작을 유지한다.

### Server/Client 경계

- Server Component/Action: 기존 Server Action과 단건 삭제 조건을 변경하지 않는다.
- Client Component/Zustand: 삭제 성공과 목록 갱신 사이에도 최초 삭제 대상을 고정하고, 성공 시 부모의 열림 상태를 확실히 닫는다. Zustand는 사용하지 않는다.

### 데이터와 Supabase

- schema 변경: 없음
- PK/FK/index: 변경 없음
- RLS 정책: 변경 없음
- Storage bucket/path/policy: 변경 없음
- migration과 rollback: 해당 없음. 코드 변경 revert로 복원할 수 있다.

## 변경 계획

1. 각 관리 화면에서 다이얼로그가 열린 시점의 삭제 대상을 별도 상태로 고정한다.
2. 성공 시 해당 다이얼로그를 닫고 삭제 대상 상태를 정리한다.
3. 목록 갱신으로 선택 행이 바뀌어도 열린 삭제 흐름이 다음 행으로 넘어가지 않게 한다.
4. 정적 검사와 관련 흐름을 검증한다.

- DB 변경 및 실제 원격 데이터 삭제는 없다.
