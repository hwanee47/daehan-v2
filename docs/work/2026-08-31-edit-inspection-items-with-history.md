# 측정이력 유지 검사항목 구조 변경

## 배경과 목적

현재 측정결과가 하나라도 있는 검사성적서는 검사항목의 기준치수·공차·개수 변경을 차단한다. 측정결과 저장 시점의 정보와 결과는 이미 측정 회차 이력으로 보존되므로, 과거 이력을 유지하면서 현재 성적서의 검사항목 구조를 새 버전으로 변경할 수 있도록 한다.

## 범위

### 포함

- 측정결과가 있는 성적서의 검사항목 구조 변경 차단 제거
- 구조 변경 전 기존 측정 회차가 존재하는지 서버에서 확인
- 과거 `inspection_measurement_runs`와 `inspection_measurement_run_items` 유지
- 현재 `inspection_report_items`를 새 구조로 교체
- 새 검사항목마다 빈 `inspection_report_measurements` 생성
- 구조 변경 저장 전 현재 측정값 초기화와 이력 유지 안내
- 구조 변경 성공 메시지에 과거 이력 유지 및 현재 결과 초기화 명시

### 제외

- 과거 측정이력 수정 또는 삭제
- 과거 회차의 검사항목을 현재 성적서로 되돌리는 복원 기능
- DB 테이블, 컬럼, 제약, RLS와 migration 변경
- 저장하지 않은 화면 입력값의 이력 보관

## 완료 조건

- [x] 측정결과가 저장된 성적서도 검사항목 구조를 변경할 수 있다.
- [x] 변경 전 측정 회차와 해당 기준치수·공차·결과가 측정이력에서 유지된다.
- [x] 변경 후 결과입력 화면은 새 검사항목과 빈 측정결과를 표시한다.
- [x] 검사항목 구조가 바뀌지 않은 수정은 현재 측정결과를 유지한다.
- [x] 사용자는 저장 전에 현재 결과가 초기화된다는 사실을 확인할 수 있다.

## 현재 구현 조사

- 관련 route/component: `src/app/(app)/inspection-reports/actions.ts`, `inspection-report-management.tsx`, 측정이력·결과입력 화면
- 관련 Supabase table/bucket: `inspection_reports`, `inspection_report_items`, `inspection_report_measurements`, `inspection_measurement_runs`, `inspection_measurement_run_items`
- 재사용할 기존 패턴: `save_inspection_measurement_run`이 측정 저장과 회차 스냅샷을 하나의 DB transaction에서 함께 생성한다.
- 문서와 구현의 차이: 이력 테이블은 현재 항목 FK 없이 당시 항목 정보를 보존하지만 애플리케이션은 현재 측정값 존재 여부만 보고 구조 변경을 차단한다.

## 설계

### UI와 반응형

- 모바일: 구조 변경이 감지된 저장 시 확인 팝업을 화면 안에 맞춰 표시한다.
- 태블릿: 기존 성적서 편집 팝업 레이아웃을 유지한다.
- 데스크톱: 확인 팝업에서 이력 유지와 현재 결과 초기화를 명확히 안내한다.
- 로딩/빈 상태/오류/권한: 기존 저장 pending, 서버 오류와 인증 처리를 유지한다. 과거 이력이 확인되지 않으면 결과가 있는 구조 변경을 중단해 데이터 유실을 방지한다.
- 접근성: 확인 팝업의 제목·설명·취소·계속 저장 버튼 및 키보드 포커스를 제공한다.

### Server/Client 경계

- Server Component/Action: 서버에서 구조 변경, 현재 결과와 기존 측정이력 존재 여부를 다시 검증한다. 이력이 확인된 경우에만 현재 항목을 교체한다.
- Client Component/Zustand: 편집 초기값과 제출값을 비교해 구조 변경 가능성을 안내하되 최종 판단은 서버에서 수행한다.

### 데이터와 Supabase

- schema 변경: 없음
- PK/FK/index: 현재 항목 삭제 시 현재 측정행은 기존 cascade 정책으로 삭제되며, 이력 항목의 `source_report_item_seq`는 FK가 아니므로 과거 이력은 유지된다.
- RLS 정책: 변경 없음
- Storage bucket/path/policy: 변경 없음. 이력 이미지 경로 보존 정책 유지
- migration과 rollback: migration 없음. 차단 조건과 확인 UI를 복구하면 기존 동작으로 되돌릴 수 있다.

## 변경 계획

1. 성적서 편집에서 검사항목 구조 변경 여부를 클라이언트와 서버에서 동일 기준으로 판단한다.
2. 현재 측정결과가 있으면 해당 성적서의 측정 회차와 회차별 항목 존재 여부를 검증한다.
3. 이력이 있으면 차단하지 않고 현재 검사항목과 빈 측정결과로 교체한다.
4. 구조 변경 저장 전 확인 팝업과 변경 성공 메시지를 추가한다.
5. 구조 미변경 수정, 구조 변경, 이력 조회와 새 결과 입력을 검증한다.

## 위험과 승인 사항

- 구조 변경 후 현재 결과입력 화면의 기존 값은 비워지며 과거 값은 측정이력에서만 조회한다.
- 현재 DB 결과가 존재하지만 대응하는 측정이력이 없는 비정상 데이터는 자동 변경하지 않고 오류로 중단한다.
- 순번 위치만 변경하는 경우는 구조 변경이 아니므로 기존 측정결과를 유지한다.
- DB 구조와 기존 이력 데이터는 변경하지 않는다.

## 결과

- 변경: 현재 측정값 또는 비고가 있는 성적서의 검사항목 구조 변경 시 확인 팝업을 표시하고, 서버에서 최신 측정이력이 현재 항목 구조와 일치할 때만 새 항목과 빈 현재 측정행으로 교체한다. 기존 측정 회차와 회차 항목은 삭제하지 않는다.
- 검증: `npm run lint`, `npx tsc --noEmit`, `npx next build --webpack`, `git diff --check` 통과
- 미실행: 실제 운영 데이터 변경을 동반하는 브라우저 저장 시나리오는 자동 실행하지 않았다. 모바일·태블릿·데스크톱 수동 시각 QA와 실데이터 이력 조회 확인이 남았다.
- 남은 위험/후속 작업: 현재 결과와 일치하는 최신 이력이 없는 비정상 데이터는 안전을 위해 구조 변경을 차단한다. 과거 회차 복원 기능은 별도 작업이다.
