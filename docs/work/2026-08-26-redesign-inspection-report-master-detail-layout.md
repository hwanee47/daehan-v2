## 배경과 목적

현재 성적서 관리 화면은 조회조건과 전체 너비 목록 중심이라, 성적서를 선택한 뒤 내용을 파악하려면 수정 팝업을 열어야 한다. 조회조건 영역을 제거하고 왼쪽 마스터 목록과 오른쪽 선택 상세를 동시에 배치해 탐색과 확인을 빠르게 한다.

## 범위

### 포함

- 조회조건 폼과 조회·초기화 기능 제거
- 왼쪽에 성적서 마스터 목록 표시
- 목록의 행을 클릭하면 오른쪽에 선택한 성적서의 기본정보 표시
- 오른쪽에 선택 성적서의 품목 이미지와 검사항목(기준치수, 공차) 표시
- 등록·수정·삭제 기능과 기존 편집/삭제 Dialog 유지
- 좁은 작업 패널에서는 목록과 상세를 위아래로 전환하는 container 반응형 적용
- 목록 선택의 키보드 조작과 선택 상태 표시

### 제외

- 검사성적서 측정 화면 변경
- 저장 동작, 데이터 조회 방식, DB schema/RLS 변경
- 새로운 검색·필터 기능 추가
- 편집 Dialog 내부 레이아웃 변경

## 현재 구현 조사

- 관련 route/component: `src/app/(app)/inspection-reports/page.tsx`, `inspection-report-management.tsx`, `data.ts`, `types.ts`
- 관련 Supabase table/bucket: `inspection_reports`, `inspection_report_items`, `inspection_report_measurements`; 조회 구조만 재사용하며 변경하지 않는다.
- 재사용할 기존 패턴: 현재 선택 상태, 코드명 매핑, 등록/수정/삭제 Dialog, 품목 이미지 전체화면 Dialog
- 문서와 구현의 차이: 현재 화면은 container breakpoint를 사용하지만 조회조건과 전체 너비 테이블 구조다. 이번 작업에서 마스터·상세 구조로 교체한다.

## 설계

### UI와 반응형

- 모바일/좁은 분할 패널: 마스터 목록 위, 선택 상세 아래의 단일 열. 각 영역은 자체 가로 overflow를 허용한다.
- 태블릿: 사용 가능한 workspace 너비가 충분해질 때 약 40:60 비율의 2열로 전환한다.
- 데스크톱: 왼쪽 목록은 번호·기종·품목상세코드·고객명·판정을 중심으로 압축하고, 오른쪽은 기본정보와 이미지·검사항목을 읽기 전용으로 표시한다.
- 로딩/빈 상태/오류/권한: 기존 서버 로딩과 인증 경계를 유지하고, 데이터 없음 및 선택 없음 안내를 각각 제공한다.
- 접근성: 목록 행은 키보드로 선택 가능하게 하고 `aria-selected`와 명확한 focus 표시를 제공한다. 상세 영역 제목은 선택 성적서와 연결한다.

### Server/Client 경계

- Server Component/Action: 기존 page 데이터 조회와 저장·삭제 Server Action을 변경하지 않는다.
- Client Component/Zustand: 선택된 성적서 일련번호는 `InspectionReportManagement`의 지역 상태로 유지한다. 전역 store는 사용하지 않는다.

### 데이터와 Supabase

- schema 변경: 없음
- PK/FK/index: 변경 없음
- RLS 정책: 변경 없음
- Storage bucket/path/policy: 변경 없음. 기존 품목상세 이미지 URL만 표시한다.
- migration과 rollback: 해당 없음. UI 컴포넌트 변경을 되돌리면 복구된다.

## 변경 계획

1. 조회조건과 필터 상태·아이콘·파생 목록 코드를 제거한다.
2. 액션 영역 아래를 마스터 목록과 선택 상세의 container 반응형 2열 구조로 변경한다.
3. 선택 상세에 기본정보, 이미지, 최종판정 및 검사항목 표를 구성한다.
4. 목록의 클릭·더블클릭·키보드 선택과 빈 상태를 연결한다.
5. lint, typecheck, build와 주요 workspace 폭에서 레이아웃을 검증한다.

## 위험과 승인 사항

- 좁은 분할 패널에서 두 영역을 동시에 가로 배치하면 정보가 과도하게 압축되므로, workspace 너비가 작을 때는 위아래 배치한다.
- 조회조건을 완전히 제거하므로 데이터가 많아질 경우 탐색성이 낮아질 수 있다. 이번 범위에서는 요청대로 검색 UI를 남기지 않는다.
- DB 및 외부 시스템 변경은 없다.
