## 배경과 목적

로그인 사용자의 `public.users.role`에 따라 메인 헤더의 기준정보 메뉴 노출을 구분한다. `admin`은 메뉴를 볼 수 있고 `user`와 비로그인 사용자는 메뉴를 볼 수 없게 한다.

## 범위

### 포함

- 홈 Server Component에서 현재 사용자의 `name`, `role`을 함께 조회한다.
- `role = 'admin'`일 때만 `ReferenceInformationMenu`를 렌더링한다.
- `user`, 비로그인, 프로필 조회 실패 시 기준정보 메뉴를 렌더링하지 않는다.

### 제외

- 데이터베이스 schema, RLS 또는 migration 변경
- 하위 관리 페이지 생성
- 관리자 페이지 접근 제어
- 역할 변경 UI
- 검사성적서 메뉴 변경

## 완료 조건

- [x] `admin` 사용자는 기준정보 메뉴를 볼 수 있다.
- [x] `user` 사용자는 기준정보 메뉴를 볼 수 없다.
- [x] 비로그인 사용자는 기준정보 메뉴를 볼 수 없다.
- [x] 프로필 조회 실패 시 안전하게 메뉴를 숨긴다.
- [x] 기존 사용자 이름 표시와 검사성적서 메뉴는 유지된다.

## 현재 구현 조사

- 관련 route/component: `src/app/page.tsx`, `src/app/reference-information-menu.tsx`
- 관련 Supabase table/bucket: `public.users`; bucket 해당 없음
- 재사용할 기존 패턴: 홈 Server Component의 현재 사용자 인증과 본인 프로필 조회
- 문서와 구현의 차이: 현재 프로필 조회는 `name`만 가져오며 기준정보 메뉴는 역할과 관계없이 항상 렌더링된다.

## 설계

### UI와 반응형

- 모바일: `user`에게 기준정보 메뉴 공간도 남기지 않는다.
- 태블릿: 역할에 따른 단순 노출 전환만 적용한다.
- 데스크톱: 역할에 따른 단순 노출 전환만 적용한다.
- 로딩/빈 상태/오류/권한: 별도 로딩 UI는 없으며 역할이 없거나 조회가 실패하면 비관리자로 취급한다.
- 접근성: 숨김 CSS가 아니라 서버에서 렌더링하지 않아 포커스 대상과 접근성 트리에도 노출하지 않는다.

### Server/Client 경계

- Server Component/Action: 홈 페이지에서 인증 사용자와 `users.role`을 조회하고 관리자 여부를 판정한다.
- Client Component/Zustand: 기존 메뉴의 열림 상태만 유지하며 역할 정보는 Client Component에 전달하지 않는다.

### 데이터와 Supabase

- schema 변경: 해당 없음 — 기존 `public.users.role`을 사용한다.
- PK/FK/index: 해당 없음
- RLS 정책: 기존 본인 프로필 조회 정책을 사용한다.
- Storage bucket/path/policy: 해당 없음
- migration과 rollback: 해당 없음

## 변경 계획

1. 홈의 프로필 조회에 `role`을 포함한다.
2. 사용자 이름과 관리자 여부를 함께 반환하도록 조회 함수를 정리한다.
3. 관리자일 때만 기준정보 메뉴를 렌더링한다.
4. lint, typecheck와 역할별 렌더링 분기를 검증한다.

## 위험과 승인 사항

- 메뉴 숨김은 보안 경계가 아니다. 관리 페이지가 추가될 때 서버 접근 검사와 RLS를 별도로 적용해야 한다.
- 인증·권한 기반 렌더링 변경이므로 구현 전 사용자 승인이 필요하다.
