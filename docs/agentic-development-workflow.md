# 에이전틱 개발 워크플로

## 1. 목적

AI 에이전트와 사람이 작업 범위, 판단과 검증 결과를 같은 형식으로 공유하기 위한 흐름이다.

## 2. 작업 분류

- **Small**: 한두 파일의 명확한 수정. 별도 작업 문서는 선택 사항이다.
- **Standard**: 여러 파일, 신규 UI, DB query 또는 상태 변경. `docs/work/`에 제안 작업 문서를 만들고 구현 전 사용자 승인을 받는다.
- **Architecture**: 인증·데이터 계층·공통 컴포넌트·최상위 구조 변경. 구현 전 사용자 승인이 필요하다.
- **Data migration**: 테이블, 컬럼, 제약, 인덱스, RLS, DB 함수·trigger, Storage 정책 또는 데이터 변환. 로컬 파일 작성을 포함한 구현 전 사용자 승인이 반드시 필요하다.

## 3. 기본 흐름

아래 1~4단계는 모든 새 작업의 필수 시작 게이트다. 다른 skill, 플러그인 또는 도메인별 workflow보다 먼저 수행한다.

1. `AGENTS.md`와 이 문서를 읽고 요청과 완료 조건을 정리한다.
2. 요청을 Small, Standard, Architecture, Data migration 중 하나로 분류한다.
3. 관련 기준 문서와 실제 인접 코드를 확인한다.
4. Standard 이상은 `docs/templates/work-template.md` 형식으로 `제안` 단계의 작업 문서를 `docs/work/YYYY-MM-DD-작업명.md` 파일명으로 작성하고 사용자에게 제안 내용을 공유한다. 날짜는 문서 작성일을 사용한다. 단, DB 작업은 승인 전 작업 문서 파일도 생성하지 않고 대화에서 초안만 제시한다.
5. 사용자의 최초 작업 요청과 구분되는 명시적 승인 응답을 기다린다. 최초 요청의 “만들어줘”, “구현해줘”, “변경해줘” 같은 표현은 4단계 제안에 대한 승인으로 간주하지 않는다.
6. 승인 응답을 작업 문서에 기록하고 단계를 `승인`으로 바꾼다. 승인 전에는 읽기 전용 조사와 제안 작업 문서 수정 외에 설계안·시각안 생성, 애플리케이션 코드 수정, 개발 서버 실행 또는 외부 시스템 변경을 하지 않는다.
7. DB 변경은 파괴적 변경 여부와 관계없이 스키마, 권한, 영향 범위와 rollback 계획을 먼저 제시하고 별도로 명시적 승인을 받는다.
8. 불확실한 요구사항과 외부 시스템 영향도 구현 전에 승인받는다.
9. 승인된 범위만 `진행` 단계로 전환해 작은 단위로 구현하고 기존 경계를 보존한다.
10. lint, typecheck, 테스트와 필요한 UI 확인을 수행하며 작업 문서를 `검증` 단계로 갱신한다.
11. 변경, 검증, 미실행 항목과 남은 위험을 기록한 뒤에만 `완료` 단계로 전환한다.

시작 게이트가 끝나기 전에는 구현을 전제로 한 질문, 시각안 생성, 파일 생성·수정 또는 개발 서버 실행을 하지 않는다. 작업 분류와 요구사항 파악에 필요한 읽기 전용 저장소 조사와 Standard 이상에서 요구되는 제안 작업 문서 작성만 예외다. 외부 skill이나 플러그인의 흐름이 필요하면 시작 게이트와 승인 게이트를 통과한 뒤 연결한다.

## 4. 승인 필요 항목

- 모든 Standard, Architecture, Data migration 작업의 제안 범위. DB 변경이 없어도 예외로 보지 않는다.
- 모든 DB 스키마 및 migration 변경. 신규 테이블처럼 추가만 하는 변경도 포함한다.
- 로컬 migration SQL 파일 생성·수정, DB 타입 생성과 해당 스키마를 전제로 한 애플리케이션 코드 변경
- 기존 데이터 삭제·변환, 컬럼 타입 축소와 rollback이 어려운 migration
- RLS 완화, public bucket 전환과 Service Role 사용 확대
- 인증 방식 또는 세션 저장 위치 변경
- 공개 URL, 환경변수 의미와 외부 API 계약 변경
- 새로운 최상위 라이브러리나 인프라 도입
- 요청 범위를 넘어선 대규모 리팩터링

승인은 제안 내용을 공유한 뒤 받은 별도의 사용자 응답이어야 한다. 에이전트가 “별도 승인 사항 없음”이라고 자체 판단해 승인 단계를 생략할 수 없다. 승인 범위가 모호하거나 일부만 승인됐다면 구현하지 않고 범위를 다시 확인한다.

## 5. Supabase 작업 흐름

1. 기존 스키마와 호출부를 읽기 전용으로 조사한다.
2. 테이블 목적, 소유자와 데이터 수명을 정의한다.
3. 컬럼, 제약, FK, 인덱스와 삭제 정책의 제안을 대화로 제시한다.
4. RLS의 `select/insert/update/delete`, Storage 정책, 영향 범위와 rollback 계획을 제시한다.
5. 요청과 다른 보안·설계 결정을 제안한다면 이유와 대안을 설명한다.
6. 사용자에게 구현 승인을 요청하고 명시적인 승인 응답을 기다린다.
7. 승인 후에만 작업 문서와 migration SQL을 작성한다.
8. 로컬 Supabase는 구성하지 않는다. 연결된 원격 `daehan` 프로젝트에서 `supabase db push --dry-run`으로 적용 대상을 확인한 뒤 migration을 적용한다.
9. 원격 migration 기록과 후속 dry run이 최신 상태인지 확인하고, 익명 사용자·본인·다른 사용자·관리자 케이스를 검증한다.
10. 승인 범위에 포함된 경우 생성 타입과 애플리케이션 query를 연결한다.

“테이블을 만들어줘”, “migration을 추가해줘” 같은 최초 요청만으로 6단계의 승인을 대체하지 않는다. 승인 전에는 파일을 생성·수정하거나 원격 DB에 명령을 실행하지 않는다.

## 6. 완료 보고

- 구현 결과를 먼저 설명한다.
- 주요 변경 파일을 연결한다.
- 실행한 검증과 결과를 적는다.
- 실행하지 못한 검증과 이유를 적는다.
- migration 실행처럼 사용자가 해야 할 후속 작업을 분리한다.
